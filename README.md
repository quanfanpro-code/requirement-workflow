# 📋 需求先行六阶段开发工作流（完整版）

> 一个帮你把开发任务做稳做牢的工作流工具。  
> 专门治「需求没想清楚就写代码」这个毛病。

---

## 🤔 这玩意儿是干嘛的

你平时开发功能的时候，是不是经常这样：

- 「先写代码再说」→ 写到一半发现方向错了，白干
- 「需求大概清楚」→ 做到一半发现漏了关键场景
- 「先上线再补测试」→ 结果永远没补
- 「验收就是点两下」→ 上线后出 bug 才发现没测到位

这个工作流就是专门治这些毛病的 👊

它是一个 **6 步走的标准流程**，每一步都规定了「先看什么资料、再做什么事」，保证：
- ✅ 需求想清楚了再动手
- ✅ 方案比较过了再选
- ✅ 测试写好了再写代码
- ✅ 验收做完了再交付

---

## 🧠 这 6 步是怎么走的（讲人话）

把你的开发任务想象成 **「盖房子」**：

### 第 1 步：需求澄清 —— 📐 画图纸

**干啥**：把「我要盖个房子」变成「要盖多大的、几层、几个卧室、什么风格」。

具体来说：
- 先看项目背景和已有资料，搞明白现状
- 然后逐条追问关键问题：
  - 这个功能给谁用？
  - 解决了什么问题？
  - 什么算「做完了」？
  - 什么情况绝对不算做完了？
  - 有没有现成的方案可以用？
- 如果涉及不了解的外部信息（比如竞争对手怎么做、有没有现成的库），去网上查清楚
- 最后写一份需求文档，至少包括：
  - 背景和问题
  - 谁用、怎么用
  - 做什么 + 明确不做什么
  - 验收标准（怎么才算做好）
  - 风险点

**产出**：一份需求文档 📄

**🛑 到这里要停下来给你看** → 确认没问题了再走下一步。

---

### 第 2 步：方案设计 —— 🏗️ 定结构

**干啥**：想 2~3 个不同的实现方案，比较它们的优缺点，选一个。

具体来说：
- 基于第 1 步确认的需求，想几套方案
- 每套方案要说明：
  - 要改哪些文件
  - 难度有多大
  - 会不会影响现有功能
  - 好不好测试
  - 万一做错了能不能回退
- 如果涉及不熟悉的技术，先去查资料搞明白再设计方案
- 关键术语一旦定下来，就写成文档，后面统一用
- 只有重要决策才写正式记录，不需要每个小选择都写

**产出**：一份设计方案 📄

**🛑 到这里要停下来给你看** → 你选一个方案，再走下一步。

---

### 第 3 步：实施计划 —— 📝 列任务清单

**干啥**：把方案拆成一个个可以动手干的小任务。

具体来说：
- 每个任务必须满足「先写一个会失败的测试 → 写最少代码让测试通过 → 检查有没有问题」
- 写明每个任务要改哪些文件、怎么验证
- 任务排好先后顺序（依赖关系）
- 默认一个任务干完再干下一个，不会同时开多个

**产出**：一份实施计划清单 ✅

**🛑 到这里要停下来给你看** → 你确认计划没问题，再开始写代码。

---

### 第 4 步：编码执行—— 🏗️ 开干（先写测试再写代码）

**干啥**：按计划一个个任务干，每个任务都走「红 → 绿 → 重构」三步：

**每个任务的循环**：
1. 🔴 **红**：先写一个测试，这个测试现在肯定会失败（因为代码还没写）
2. 🟢 **绿**：只写让测试通过的最少代码，不写多余的
3. 🔧 **整理**：在测试的保护下，改掉刚才写的临时代码里的问题
4. ✅ **验证**：跑一下全部测试，确认没搞坏别的东西

**重复上述步骤**，直到所有任务干完。

**原则**：
- 先写测试再写代码，不是先写代码再补测试
- 只写最少量的代码让测试通过，不提前写「未来可能会用到」的代码
- 测试至少要覆盖：正常情况、边界情况、出错情况

**遇到真正难查的 bug 怎么办**：
- 普通的测试失败不算难查，它本来就是 TDD 的正常红灯，继续按红、绿、整理、验证推进
- 如果问题跨环境才出现、现有证据解释不了，而且一次针对性修复后仍复现，工作流会自动进入 `diagnosing-bugs` 诊断分支
- 这个分支会先稳定复现、列出可验证的原因假设、逐项取证，再修共同根因；修完后回到原来的 TDD 验证步骤
- `diagnosing-bugs` 的正文、脚本模板和来源记录已经完整放在本项目里，使用时不需要另外安装，也不会读取电脑上别的 skills 目录

**产出**：可以运行的代码 + 配套的自动化测试 ✅

---

### 第 5 步：验收审查 —— 🔍 全面检查

**干啥**：把前面所有的产出从头到尾检查一遍，看看有没有遗漏或做错。

具体来说：
- 对照需求文档：该做的都做了吗？
- 对照设计方案：结构跟设计的一致吗？
- 对照实施计划：每个任务都完成了吗？
- 检查代码有没有安全问题、性能问题
- 检查测试是不是真的有用（不是只走个过场）
- 把发现的问题按严重程度修掉

如果发现需求或设计有问题，**退回去重做**，不能只改表面。

**产出**：一份审查报告 + 修复后的代码 ✅

---

### 第 6 步：交付完成 —— 🚀 收尾

**干啥**：最后一次全部检查，确认没问题了，自动帮你提交并推送代码。

具体来说：
- 重新跑一遍全部测试，确认都是绿的
- 检查工作区状态，列出所有改动的文件
- **默认自动执行**，不用再问你要不要：
  - 提交到本地仓库（commit）
  - 推送当前分支到远程仓库（push）
- 推送失败、没有远程仓库时，会如实告诉你实际结果，不假装成功
- 创建合并请求（PR）、合并到别的分支、清理临时工作区这些动作，仍然只在你说要的时候才做

## 🎯 什么时候用它

| 场景 | 建议 |
|---|---|
| 做一个全新功能 | ✅ 必须用 |
| 修改一个已有功能 | ✅ 建议用 |
| 修一个 bug | ✅ 建议用（除非只是改个错别字） |
| 只是改个文案 | ❌ 不用走 6 步，直接改 |

**注意**：这个工作流有一个硬规矩——**不管任务看起来多小，都不能自己判断「这个太小了，跳过几步」**。必须完整走完 6 步。如果你觉得某个任务确实很简单，在第 1 步停下来跟确认就好。

---

## 🚫 红线（绝对不能做的事）

| 禁止行为 | 错误例子 |
|---|---|
| 自己判断任务小就跳步骤 | 「只是改个错别字，直接处理，不走 6 步。」 |
| 用自己编的问题替代内置追问 | 「大概问两句就行，不用那么细。」 |
| 缺了参考资料就凭经验做 | 「少一个参考文件不影响，按经验来。」 |
| 没有等你确认就进入下一步 | 「方案大致清楚了，先写代码再说。」 |
| 没有你授权就开多个任务并行 | 「这两个任务没关联，同时做快一点。」 |
| 没有你授权就合并、清理分支 | 「直接帮你合并并清理分支。」 |
| 没有刚刚跑过的验证证据就说做完了 | 「代码看起来没问题，应该算完成了。」 |

---

## 🛡️ 出问题了怎么办（故障处理）

| 出什么问题 | 怎么处理 |
|---|---|
| 本地文件缺失或损坏 | 停止工作流，告诉你「技能包不完整」，不凭经验代替 |
| 查资料的网络连不上 | 记录查不到的项，等你决定是等联网还是标记为「猜测」 |
| 测试一直通不过 | 找到根本原因，缩小改动范围再试；如果还不行，停下来报告 |
| 审查发现需求不成立 | 退回第 1 步修改需求，不修表面症状 |
| 不是 git 仓库 | 跳过 git 交付动作（提交、推送），只做文件级验证 |

## 🔄 怎么检查上游来源有没有新版本

维护时运行 `python scripts/check_upstream.py`。脚本会按 `references/SOURCES.json` 中的独立来源逐项检查；本地只保留已经登记的来源，不会读取电脑上其他 skills 目录。

仓库地址、分支、固定提交号、来源目录、快照校验值、本地文件清单和适配说明，都记录在 `references/SOURCES.json`；本地依赖关系记录在 `references/DEPENDENCY-MAP.md`。升级后再运行 `python scripts/validate_bundle.py` 和集成测试，就能确认自包含关系没有断。
